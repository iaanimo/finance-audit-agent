# 财务报销审核受控 Agent

> **把 LLM 关进笼子里的报销审核流程。**
>
> 通用 agent 项目人人都在做。这个项目的特别之处在于它处理的业务**错不起** ——
> 财务审核的结论必须可复现、可追溯、可审计。

一句话概括设计原则：

> ### LLM 只管「读」，规则引擎管「判」。

即使模型抽风，审核结论也一样。

---

## 为什么这么设计

财务审核里没有"模型这次抽风了"这种解释。一条错误的审核意见，轻则让不合规的费用入账，
重则是一次审计事故。所以判定的每一环都必须能回答三个问题：

1. **依据是什么？** —— 每条结论绑定一个制度条款号，附带制度原文
2. **能不能复现？** —— 判定由 17 条纯 Python 规则完成，**零 LLM**，同输入同输出
3. **谁能改它？** —— 只有人能推翻系统建议，而且**必须留下书面理由**

于是就有了这条分层管线：

```
   发票文件（PDF / 图片）
        │
        ├─ ① 抽取层   LLM 允许参与、允许出错 ······· finance/extractor.py
        │     PDF 文本层（确定性，不联网）优先；扫描件/照片走视觉模型兜底
        │     出错不要紧 —— 下一层会抓住它
        │
        ├─ ② 校验层   ★ 零 LLM ★ 绝不允许出错 ····· finance/rules.py
        │     17 条规则，每条绑定制度条款、每条带证据字段
        │     单条规则抛异常只降级为「转人工」，绝不让整单审不下去
        │
        ├─ ③ 叙述层   LLM 只把结论翻译成人话 ······· finance/guard.py
        │     护栏两道：① 数字必须能在 findings 里找到（防编事实）
        │               ② 结论倾向必须与系统建议一致（防说反）
        │     任一不过 -> 整段丢弃换模板
        │
        ├─ ④ 人审门   ★ 只有人能批准 ★ ············· finance/audit.py::decide
        │     系统最多把单子推到 pending_review
        │     推翻系统建议必须书面说明理由，理由与系统原判断一并留档
        │
        └─ ⑤ 留痕层   只追加，不可修改 ·············· finance/store.py
```

## 快速开始

```bash
# 1. 安装（首次约 1-3 分钟）
setup.bat            # Windows 双击

# 2. 启动
start.bat            # Windows 双击

# 3. 打开审核台
#    http://127.0.0.1:8000/audit
```

手动方式：

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
cp .env.example .env        # 填入 API Key —— 不填也能跑，见下
.venv/Scripts/python.exe server.py
```

> **API Key 是可选的。** 不配叙事模型 Key，审核结论**完全不受影响**，
> 只是审核意见退化为模板文字。不配视觉模型 Key，PDF 文本层路径照常工作，
> 只是扫描件无法兜底。这是设计目标，不是降级。

### 演示前必做

页面上点一下 **「清空演示数据」**。排练跑过的单子会留在查重台账里，
正式演示再传同一张样本，R004 会命中"重复报销"，**开场全绿基线当场翻车**。

## 17 条规则

制度原文在 `finance/policies/reimbursement.md`，机器可读规则表在 `rules.yaml`，
判定实现在 `finance/rules.py`。**三方由测试锁死，缺一即红。**

| 规则 | 判什么 | 严重度 | 制度条款 |
|---|---|---|---|
| R001 / R002 | 发票抬头、纳税人识别号 | FAIL | 3.1 |
| R003 | 开票日距提交 ≤ 60 天，不得跨年 | FAIL | 3.2 |
| R004 | 发票代码+号码查重（**有状态，接台账**） | FAIL | 3.3 |
| R005 | 市内交通单次 ≤ 200 元 | FAIL | 4.1 |
| R006 | 餐饮人均 ≤ 150 元且须注明人数事由 | FAIL / **WARN** | 4.3 |
| R007 | 住宿分城市限额（一线 600 / 其他 400 每晚） | FAIL | 4.2 |
| R008 | 办公用品超 2000 元须附清单 | **WARN** | 4.4 |
| R009 / R010 | 发票类型白名单、金额一致性 | FAIL | 3.4 / 3.5 |
| R011 | 费用类型可映射到会计科目 | **WARN** | 5.1 |
| R012 | **同日同销售方连号 → 疑似拆单** | **WARN** | 5.2 |
| R013 / R014 | 凭证借贷平衡、部门预算余额 | FAIL | 6.1 / 5.3 |
| R015 | **票面提示注入**（备注栏塞指令） | **WARN** | 3.8 |
| R016 | **大小写金额一致性**（防篡改） | FAIL | 3.7 |
| R017 | **适用税率**与票面项目相符 | FAIL | 3.6 |

### 三态语义

| 严重度 | 含义 | 制度原文措辞 |
|---|---|---|
| `PASS` | 通过 | —— |
| `FAIL` | **事实性违规**，系统直接驳回 | "不得报销" / "不予受理" |
| `WARN` | **概率性怀疑**，系统只提示、转人工 | "提交人工复核" / "退回补充" |

R012 连号是**怀疑**不是**事实** —— 系统不应该替人给报销人定罪。
同一条规则内也可以逐条覆盖严重度：R006 的"人均超标"是 FAIL，
"未注明人数"是 WARN（信息缺失只是退回补充）。

## 四条可执行的不变量

「受控」不该是架构图上的一句话，而应该是**测试挂了就红**的东西。
见 `tests/test_finance.py`：

| 不变量 | 怎么守 |
|---|---|
| **规则表 ↔ 制度原文 ↔ 代码 三方一致** | 每个 `rule_id` 必须在制度里找得到条款、在代码里找得到 checker；且每条规则必须归属到状态机的一个阶段（防止"写了规则但编排不跑它"） |
| **能改审核状态的入口从不落到 LLM 手里** | 结构性断言：整个 `finance/` 包里只有 `audit.py` 会改写审核单状态 |
| **推翻系统建议必须留书面理由** | `suggested_status` 原封不动留在日志里，人的决定追加在旁边 |
| **LLM 叙述不能造事实、不能改结论** | 护栏两道：逐数字比对 findings（防编事实）；解析叙述里的「建议X」并与 `suggested_status` 比对（防说反）。任一不过 -> 整段换模板 |

第三条的要害在于：**系统有意见，人有权力，但权力留下痕迹。**

```json
{"event": "decided", "suggested_status": "REJECTED", "decision": "APPROVED",
 "operator": "张伟", "overridden": true,
 "override_reason": "客户临时改期，超标部分员工自付，已电话确认"}
```

注意 `suggested_status` 仍然写着 `REJECTED` —— 系统原来的判断没有被人的决定抹掉。

## 评测

```bash
.venv/Scripts/python.exe scripts/run_eval.py --report eval/report.md
```

13 张样本票跑一遍，逐条核对「预期命中」vs「实际命中」。**完全离线**：
走 PDF 文本层，不调视觉模型、不调 LLM —— 同一批样本跑一百遍结果一致。

当前结果：

| 指标 | 数值 |
|---|---|
| 端到端完成率 | **100%**（13/13） |
| 规则召回率 | **100%**（12/12） |
| 误报数 | **0** |
| 字段抽取正确率 | **100%**（13/13） |

**这些数字的边界要说清楚**，否则它们会被高估：

- **样本与抽取正则是同一套版式**。样本票由 `scripts/make_samples.py` 生成，
  抽取正则是照这个版式写的 —— 所以「抽取正确率 100%」衡量的是
  **样本 → 抽取引擎的一致性**，**不是对任意真实发票的泛化能力**。
  真实发票版式千差万别，这一点没有验证过（这也正是保留视觉模型兜底路径的原因）。
- **规则召回 12/12 的分母**是「有对应端到端样本的规则（12 条）」，
  不是全部 17 条。另外 5 条（R004 / R009 / R010 / R011 / R013）由单元测试覆盖，
  没有专门的端到端样本。

> 评测脚本在开发中抓到过两次真实错误：给样本编了连号导致 R012 误报，
> 以及测试里写死了过期的规则条数被自己的护栏拦下。**它是有效的安全网，不是摆设。**

## 几个值得说的设计取舍

### 税率校验为什么放行 3%

R017 的放行集合是 **{法定税率} ∪ {简易计税征收率 3%}**。

因为**发票票面看不出销售方是一般纳税人还是小规模纳税人**。
小规模纳税人适用简易计税，票面税率就是 3%。如果照法定税率硬卡，
每一张小规模纳税人的票都会被误判。**宁可漏报，不可误杀** ——
在审核意见这种场景下，一次误杀会让整条链路的可信度崩掉。

### 制度为什么是 YAML 不是提示词

把"请遵守公司制度"写进 system prompt，模型判不判、判成什么，你无法回答，也无法复现。
改成结构化配置之后：每条规则绑定条款号，结论能直接指回制度原文；
阈值改一处即全局生效；制度原文被一起读进来供一致性测试比对。

**规则命中时该引哪条制度是已知的，不需要"检索"出来** ——
这比 RAG 更确定，也是这里没有引入向量检索的原因。

### 抽取允许出错

因为下面一层会抓住。把不确定性**圈在一层里**，比试图让模型"更准"要可靠得多。
PDF 文本层路径完全不联网、可复现，在本项目的样本版式上能完整抽出全部关键字段
（含买卖双方两个"纳税人识别号"的归属区分）。

**但这条路径是按样本版式写的正则，不是通用发票解析器** —— 版式一变就可能抽空。
所以保留了视觉模型兜底（`use_vision=True`），并让规则引擎对「抽不到的字段」
统一判 WARN 转人工，而不是猜。

### 记账凭证为什么把税额拆成一行

凭证的借方是**两行**（不含税金额 + 进项税额），贷方一行价税合计：

```
借  管理费用-差旅费-住宿费        1,556.60
借  应交税费-应交增值税（进项税额）   93.40
贷  其他应付款-员工报销           1,650.00
```

原因：如果借方只写一行总额、金额又永远等于贷方，那么 R013「借贷平衡」
就是一条**恒真式** —— 校验永远通过，等于没校验。拆开之后，
`1556.60 + 93.40 == 1650.00` 才是一次真的算术校验。
票面缺税额时退回单行写法，不影响主流程。

## 已知限制（如实说）

- **申报数据没有锚点，规则可以被"合法地"绕过。** 申请单里的提交日期（以及金额、人数、晚数）
  由报销人手填，服务端不校验它与服务器时间或上游单据的关系。
  实测：同一张超期发票，把提交日从 90 天前改成 42 天前，R003 就从 FAIL 变成 PASS。
  **生产环境里这些字段必须来自服务器收单时间和已审批的 OA 申请单，报销人不可写。**
  本作品保留手填，是为了让 13 张样本的时效场景不因日期流逝而失效。

  > 这条边界恰好印证了本项目的立论：**机器只能证明"单据之间自洽"，
  > 证明不了"申报本身真实"。** 所以真实系统不允许全自动审批 ——
  > 必须有人为申报的真实性负责。

- **审批人身份不设防。** 操作人是自由文本框，可以填任何名字（张三能批张三的单）。
  真实系统必须接 SSO + 角色控制，并强制"经办与审核不得同人"（不相容岗位分离）。

- **视觉抽取路径没有人工核对卡点。** PDF 文本层是确定性的、可信；
  但开启 `use_vision=True` 时，模型读图的结果会**直接进入规则引擎** —— 金额读错就会判错。
  生产环境应在送审前强制人工确认抽取到的字段。

- **没有接税局验真。** 只做到了发票类型白名单 + 抬头税号核对 + 大小写一致性。
  真实查验需要对接国家税务总局全国增值税发票查验平台，本项目未做。
  一张票面完全自洽的假票、作废票、红冲票，目前会全绿通过。
- **审批链未做动作分级。** 过账、付款、报税、披露目前共用一个"批准/驳回"闸门，
  没有按动作粒度分别授权。
- **没有回滚机制。** 审计日志是只追加的。财务意义上的"回滚"通常指**红冲**
  （红字冲销凭证）而非删除记录，与本项目"只追加不得修改"的留痕原则如何共存，
  尚未设计。
- **部门预算是静态快照**（`policies/budgets.yaml`），没有从已审批单据累加。
- **单用户、无鉴权。** 定位是演示项目，不是生产系统。

## 项目结构

```
finance/                     核心领域包
  models.py                  数据契约、金额 Decimal、中文大写金额解析
  rules.py                 ⭐ 17 条规则 —— 判定权的唯一所在
  audit.py                 ⭐ 唯一状态变更入口、六态状态机
  extractor.py               抽取（PDF 文本层优先 / 视觉兜底）
  policy.py                  制度加载器
  store.py                   审核单落盘 + 只追加审计日志
  guard.py                   LLM 叙述护栏
  voucher.py                 记账凭证草稿
  policies/                  制度 md + 规则表 + 科目表 + 预算表

config/ core/ tools/         配置、叙事模型入口、文件路径约束
scripts/
  make_samples.py            合成发票生成器
  run_eval.py                评测集
static/audit.html            审核台页面
tests/test_finance.py        64 条测试（含四条不变量与 R013 非恒真校验）
```

## 关于样本数据

`finance/samples/` 下的 13 张发票**全部是合成的**，由 `scripts/make_samples.py`
用本机 Edge 的 headless 模式渲染 HTML 生成，票面页脚标注「示例样本，非真实发票」。
公司名称、纳税人识别号、销售方均为虚构。

用合成数据而不是真实发票的原因：真实发票含真实税号与消费记录，不应进入代码仓库；
而演示"住宿超标"这类边界又必须有一张恰好超标的票 —— 真实票据凑不齐这套边界。
